i Contexto

Por que este roteiro existe e quais decisões o guiam.

O Fluxy é um app de finanças pessoais cujo frontend ainda não foi construído: o repositório é um create-next-app praticamente limpo, com pastas vazias lib/api, lib/auth, components/auth. As 6 specs em front-specs/ definem um contrato de API completo e fechado (modelos, endpoints, auth/sessão, regras de negócio, catálogo de erros), mas deliberadamente não definem a UI ("a UI será definida posteriormente").

Cada fase abaixo aponta a spec de origem, o que entregar e os critérios de aceite — construção incremental dirigida pelas specs.

Decisões de arquitetura (confirmadas)

Comunicação & tokens
BFF / proxy no Next; access & refresh em cookies httpOnly server-side
Dados & estado
Server Components (leitura) + Server Actions (mutação), revalidatePath/Tag
UI
Funcional mínima + Tailwind; design visual fica para fase posterior
⚠️ Divergência intencional com a spec 0004 §1 — ela descreve o token "guardado pelo web app" sem cookie httpOnly. Isso é a decisão do backend sobre como entrega o token; o frontend pode, com mais segurança, encapsular o refresh num BFF. Não muda o contrato da API. O .env.example já usa API_BASE_URL server-only (sem NEXT_PUBLIC_), o que confirma esse caminho. Se algo conflitar com o backend durante a implementação, parar e consultar (regra SSD).

0 Fundação do projeto e contrato de tipos

Origem: 0001 (stack/princípios), 0002 (modelos), 0006 (envelope de erro).
  • lib/api/types.ts — DTOs e enums literais da spec 0002: Kind, Me, Category, Transaction, TokenPair, MessageResponse, Summary, TransactionPage. Mais o envelope { error: { statusCode, code, message, details? } } (0006 §1) e um union ApiErrorCode com todos os code do catálogo (0006 §2).
  • lib/config.ts — leitura de API_BASE_URL (server-only) com validação no boot; import "server-only".
  • lib/money.ts — utilidades de dinheiro (0002 §3): formatBRL(cents) via Intl.NumberFormat('pt-BR', { style:'currency', currency:'BRL' }) e parseBRLToCents(input). Somar sempre em centavos inteiros.
  • lib/date.ts — helpers YYYY-MM-DD para occurredAt/from/to (data pura, sem fuso) vs ISO de createdAt (0002 §4). Default do período = mês corrente (0005 RN-Rep-2).
  • Limpar boilerplate de app/page.tsx/app/layout.tsx e ajustar .env.example/.env.local.
Aceite: npm run build e npm run lint passam; tipos compilam; formatBRL(1250) → "R$ 12,50"; parseBRLToCents("12,50") → 1250.

1 Cliente HTTP, sessão (cookies httpOnly) e tratamento de erros

Origem: 0003 §1 (base/headers/rate limit), 0004 (tokens/sessão/rotação), 0006 (erros).
  • lib/api/client.ts (server-only) — fetch para API_BASE_URL que injeta Authorization: Bearer <access> (do cookie), faz parse do envelope de erro e lança um ApiError tipado com .code/.statusCode/.details.
  • lib/auth/session.ts — leitura/escrita dos cookies httpOnly access/refresh (Secure, SameSite=Lax) via cookies() do Next; helpers getSession, setSession(tokenPair), clearSession.
  • Refresh com rotação serializada (0004 §2): ao receber 401 UNAUTHORIZED numa rota 🔒, chamar POST /auth/refresh uma vez, trocar os dois tokens e repetir a chamada. Serializar para evitar corrida (rotação invalida par emitido em paralelo). Em TOKEN_INVALID/TOKEN_EXPIRED no refresh → clearSession + redirect a /login.
  • Eventos que invalidam todas as sessões (reset-password, change-password, reuso de refresh): limpar sessão local e redirecionar ao login (0004 §3).
  • lib/api/error-messages.ts — mapa code → mensagem PT-BR (0006 §3.6: reagir pelo code, mensagem própria, não a message em inglês).
  • Tratar 429 (backoff/feedback) e 5xx/rede (transitório, permitir retry, não deslogar).
Aceite: uma chamada 🔒 com access expirado dispara refresh e repete sozinha; refresh inválido desloga; ApiError.code disponível para a UI; mensagens PT-BR por código.

2 Autenticação e rotas de deep-link de e-mail

Origem: 0003 §3, 0004 §4–§6, 0005 §1 (validações), 0006 (erros de auth).

Server Actions — lib/auth/actions.ts

register, login, logout, forgotPassword, resetPassword, verifyEmail, resendVerification, changePassword. Cada uma chama o endpoint correspondente; no login, grava cookies.

Rotas / telas (App Router, UI mínima)

  • app/(auth)/login — tratar INVALID_CREDENTIALS (401) e EMAIL_NOT_VERIFIED (403 → oferecer "reenviar verificação").
  • app/(auth)/register — resposta genérica (não revela e-mail existente).
  • app/(auth)/forgot-password — sempre confirma genericamente.
  • app/verify-email — lê ?token= e chama POST /auth/verify-email (deep-link obrigatório — 0004 §5).
  • app/reset-password — lê ?token= e chama POST /auth/reset-password (deep-link obrigatório — 0004 §5).
  • app/(app)/account/change-password — após sucesso, deslogar (todas as sessões revogadas — 0004 §4.5).

Validação de UX espelhando a spec

Validação final é do servidor. E-mail algo@algo.dominio ≤ 320; senha 8..200 sem complexidade obrigatória (0004 §6 / 0005 §1). Usar details do VALIDATION_ERROR para marcar campos.

Proteção de rotas

Middleware/layout que exige sessão para o grupo (app) e redireciona não autenticado para /login.

Aceite: fluxo cadastro→verificação→login funciona ponta a ponta contra o backend local (http://localhost:3333); deep-links /verify-email?token= e /reset-password?token= funcionam; login bloqueia e-mail não verificado oferecendo reenvio; change-password desloga.

4 Categorias (CRUD + arquivamento)

Origem: 0003 §4, 0005 §2 (RN-Cat-1..5), 0006 (erros de categoria).
  • Leitura: Server Component lista GET /categories (só ativas por padrão); includeArchived=true apenas em tela de gestão/histórico (RN-Cat-4).
  • Server Actions: criar (POST), renomear (PATCH só name — kind imutável, RN-Cat-1), excluir (DELETE). Após mutação, revalidatePath da lista.
  • Nome 1..60; único por (usuário+tipo) entre ativas → tratar CATEGORY_NAME_IN_USE (409) no campo nome (RN-Cat-2).
  • Exclusão: a UI não sabe se arquivou ou apagou (ambos 204) → revalidar a lista depois (RN-Cat-3). Confirmar antes de excluir.
  • Não expor mudança de kind na edição. Não oferecer cor/ícone, subcategorias, reordenação (fora de escopo — 0001 §4).
  • Categorias padrão já vêm criadas no cadastro (RN-Cat-5) — não recriá-las.
Aceite: criar/renomear/excluir refletem na lista; nome duplicado mostra erro no campo; após excluir categoria com transações, ela some da lista ativa mas aparece com includeArchived=true.

5 Transações (CRUD, filtros, paginação por cursor)

Origem: 0003 §5, 0005 §3 (RN-Tx-1..8), 0002 (Transaction/TransactionPage), 0006.
  • Leitura: Server Component carrega a 1ª página de GET /transactions (default limit=20, ordem occurredAt desc). Filtros opcionais: from/to, categoryId, kind.
  • "Carregar mais" por cursor (RN-Tx-8): client component que reenvia a mesma query + cursor=nextCursor; para quando nextCursor === null. Sem offset, sem total. Filtros não mudam dentro de uma sequência.
  • Server Actions: criar (POST), editar (PATCH parcial — description:null limpa), excluir (DELETE, hard delete, confirmar antes — RN-Tx-7).
  • Categoria obrigatória, exatamente uma (RN-Tx-1); seletor só com categorias ativas do mesmo kind (RN-Tx-2/3/4) — filtrar por kind.
  • amountCents inteiro > 0, convertido de input BRL (RN-Tx-4 / lib/money.ts); o sinal vem do kind. Tratar INVALID_AMOUNT (400) e VALIDATION_ERROR.
  • Datas futuras permitidas em occurredAt (RN-Tx-5) — não bloquear.
  • Editar kind exige categoria compatível com o novo tipo (RN-Tx-6); manter vínculo a categoria arquivada depois é válido (não forçar troca).
  • Tratar CATEGORY_ARCHIVED (409), CATEGORY_KIND_MISMATCH (409), CATEGORY_NOT_FOUND (404) revalidando/filtrando o seletor.
  • Sem busca textual por descrição (fora de escopo — 0001 §4 / 0005 §3).
Aceite: criar despesa e receita com seletor filtrado por tipo; "carregar mais" pagina por cursor até null; editar limpando descrição; excluir com confirmação; erros de categoria/valor mostrados no campo correto.

6 Relatórios (resumo do período)

Origem: 0003 §6, 0002 (Summary), 0005 §4 (RN-Rep-1..5), 0006.
  • Server Component chama GET /reports/summary com from/to (omitidos ⇒ mês corrente, RN-Rep-2). Período inclusivo; from > to ⇒ VALIDATION_ERROR (mostrar correção).
  • Exibir totals (income/expense/balance/count); balanceCents pode ser negativo (saldo no vermelho é válido — RN-Rep-1).
  • byCategory: lista única; o frontend separa despesa/receita pelo kind ao exibir; itens com archived:true (categoria arquivada com histórico no período) devem ser exibidos, marcados como arquivados (RN-Rep-3).
  • Percentual por categoria é cálculo do cliente a partir de totalCents / total do tipo (RN-Rep-4). Não baixar todas as transações para somar — usar só o resumo (RN-Rep-5).
  • Sem export e sem timeline mês a mês (fora de escopo — 0001 §4).
Aceite: resumo do mês corrente por default; troca de período funciona e valida from>to; categoria arquivada com histórico aparece marcada; percentuais batem com os totais.

7 Endurecimento e checklist final

Origem: 0001 §3 (princípios), 0006 §3 (estratégia), produção.
  • Revisar todos os pontos "fora de escopo" (0001 §4) — garantir que a UI não oferece recorrência, orçamentos, multi-carteira, import, multi-moeda, anexos, OAuth/MFA, exclusão de conta, subcategorias, etc.
  • Conferir reação a todos os code do catálogo 0006 §2 (incluindo 429 e 5xx).
  • Garantir isolamento por usuário: frontend nunca envia userId (P2 / RN-Iso-1).
  • Conferir server-only nos módulos que tocam tokens/API_BASE_URL (guia 02-guides/data-security.md); nenhum segredo vaza para bundle client.
  • Atualizar README.md (rodar em APP_URL do backend p/ CORS — 0001 §2; setar API_BASE_URL).
Aceite: build de produção limpo; nenhuma feature fora de escopo exposta; tokens nunca aparecem em código client-side.

✓ Verificação end-to-end

  1. Subir o backend Fluxy local em http://localhost:3333 e o frontend em APP_URL (default http://localhost:3000) para satisfazer CORS (0001 §2).
  2. npm run dev e percorrer manualmente: cadastro → /verify-email?token= → login → criar categoria → criar transações (despesa/receita) → "carregar mais" → relatório do mês → editar/excluir → change-password (desloga) → forgot//reset-password?token=.
  3. Conferir no navegador que nenhum token aparece em storage/JS client (estão em cookies httpOnly) e que chamadas com access expirado se renovam sozinhas.
  4. npm run build + npm run lint sem erros. Opcional: smoke test com Playwright (02-guides/testing/playwright.md) cobrindo login + criar transação.
